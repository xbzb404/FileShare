# FileShare v1.1.2

修掉「共享目录里有文件被打开时，同步/重建共享失败并把系统提示原样显示在面板上」的问题。

## 下载

**FileShare.exe**（22.8 MB，单文件免安装、无外部依赖，Windows 10/11 x64）

## 你看到的那句话是怎么来的

在 SMB 面板上出现过的黄字：

```
Fshare: 用户打开了 Fshare 上的文件，继续这项操作会强制关闭文件。
你想继续此操作吗? (Y/N) [N]: 没有提供有效的响应。
```

它不是本程序的提示，而是 `net share /delete`（或重建同名共享）遇到「有客户端
正开着里面的文件」时弹出的**交互确认**。两个原因叠在一起：

1. **子进程没有 stdin**。打包成无控制台程序后，子进程继承到的标准输入是无效句柄，
   `net` 读不到回答，直接吐一句「没有提供有效的响应」然后失败；
2. **每次同步都在「删了重建」**。只要共享状态没变也照样先删一遍，于是任何时刻
   有人开着共享里的文件，就会被踢一次、报一次错——正在传的大文件也会中断。

## 本版改动

- 所有系统命令的子进程统一使用空输入（`stdin=DEVNULL`），任何交互式确认都不会再
  卡住或失败，也不会把 `(Y/N)` 之类的问答残渣显示到界面上
- `net share /delete` 加 `/y`：取消共享时不再询问「是否强制关闭文件」
- **同步改为幂等**：路径与权限都对就一个命令都不发（日志显示「共享已是最新，无需改动」）；
  只有路径或只读/读写真的变了才重建，重建时也不强制关闭别人的文件
- 「共享正被占用」这类情况翻译成人话（「共享正在被其它设备使用（有文件没关闭），
  本次操作已跳过」），不再把系统的英文/中文问答原样抛到面板
- 顺手修掉一个隐藏错误：取消共享时调用 `revoke_all()` 传了 `paths` 但函数签名没接，
  会抛 `TypeError` 被外层 `except` 吞掉——**退出程序时其实没有还原目录权限**，现已修好
- `exists()` 不再只认返回码：非管理员查共享会以「系统错误 5」结尾，但共享信息已经
  打印出来了，只看返回码会把已存在的共享误判成不存在，从而去重建

## 质量

- 101 项自动化测试全绿，本版新增 8 项：幂等跳过 / 权限变化才重建 / 路径变化才重建 /
  删除带 `/y` / 取消共享传递目录 / 提示文案清洗 / 成功行过滤 / 子进程 stdin 隔离
- 探针复跑：SMB 控件行为、GUI 逐页、滚轮、冒烟、托盘、流量、带宽、性能、单实例全过

## 升级说明

直接覆盖旧的 `FileShare.exe` 即可，配置文件自动兼容。若之前点过「修复局域网访问」，
目录权限与账户沿用，无需重做。
